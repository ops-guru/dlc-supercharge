# E2E Retrospective — feedback-collector Kiro Spec flow (2026-05-25)

**Test subject**: a tiny FastAPI feedback-collector web app, taken from concept to running app via the full Kiro Spec → DLC bridge flow.
**Goal**: empirically validate the v2.0.0 Python runtime and the 14 Kiro hooks under a real, end-to-end workflow that exercises every hook in the chain.
**Outcome**: app runs (POST /feedback persists correctly, returns 303 redirect per FR-8). Four distinct bug classes surfaced — all addressed by patches PR #5, #6, #7, #9. No regressions in the 334-test suite during the cascade.

## Bug #1 — id_propagate heading-format drift (PR #5)

**Discovery**: 0 of ~30 FR-x comments injected into Kiro's `requirements.md` despite `id_propagate.propagate_ids()` being called inline in the hook. Initial hypothesis: Kiro race condition (rewriting `requirements.md` after the bridge ran). Falsified by hashing: `sha256(current file) == cached source hash` → Kiro had NOT overwritten anything.

**Root cause**: `id_propagate._parse_prd_entries` regex literally hard-coded `#### FR-1 - Title` (h4 + ASCII hyphen) — the v1.1 PowerShell convention. The live `/dlc:analyze-requirements` skill emits `### FR-1 — Title` (h3 + em-dash U+2014). Parser returns `[]`, propagation is a silent no-op. The PowerShell version had been more permissive (already accepted em-dash); the v2.0 Python port inherited the *PowerShell* regex, not the *bash* regex. This was never caught because the test suite uses synthetic fixtures matching the parser's expectations — never live plugin output.

**Fix**: relax to `#{3,4}\s+(FR|NFR)-(\d+)\s+[-–—]\s+(.+)` — h3 OR h4, ASCII / en / em dash. Bounded (h2 and h5 still rejected). Plus a captured-real-plugin-output fixture under `tests/fixtures/id-prop/real-plugin-output/` so the test suite catches this class of drift going forward.

**Diagnostic upgrade**: new shared `_common.emit_propagate_outcome()` distinguishes three outcomes the prior happy-path `ID_PROPAGATED` marker silently conflated: `ID_PROPAGATED` (≥1 injected), `ID_PROPAGATE_ZERO_MATCHES` (entries parsed but below threshold), and `ID_PROPAGATE_NO_ENTRIES` (PRD parse anomaly — surfaces format drift loudly).

**Lesson**: bridge integration code MUST be tested against real plugin output, not synthetic fixtures matching the consumer's expectations. The bug is exactly the kind of producer/consumer contract drift unit tests can't catch when both producer and consumer are mocked.

## Bug #2 — premature state finalize (PR #6)

**Discovery**: `state.md` advances to Phase 3 at 19:40 UTC — but `tech-design.md` doesn't exist until 19:43 UTC (3m37s later). The hook's `finalize` step ran while the bridge was still running.

**Diagnosis**:
1. Bridge wrapper PIDs (7068, 55052) were dead by the time we checked; `claude.exe` children (20852, 55524) were still alive.
2. The hook's init `subprocess.run(claude.exe)` is correctly blocking — no early return on the bridge side.
3. So the agent must have abandoned the init Bash and run finalize as a separate Bash invocation.
4. Kiro's Bash tool appears to have an inactivity timeout (the analyze-requirements 4m35s ran fine; the produce-tech-design 7m38s did not). The bridge's `subprocess.run(capture_output=True)` is silent for the entire duration — looks hung.

**Fix**: `_common.invoke_bridge()` now spawns a daemon heartbeat thread that emits `BRIDGE_PROGRESS=verb=<v> elapsed=<N>s` to the wrapper's *own* stdout every 30s (configurable). The bridge's stdout is captured by `subprocess.run`, so anything *the bridge* prints never reaches Kiro's bash tracker — the heartbeat must come from the *wrapper*. Stops the thread cleanly when the subprocess returns. Default 30s interval, opt out via `heartbeat_interval=None`.

**Validation**: the next `on-tasks-saved` fire ran for 27 minutes (much longer than design) and the init Bash survived intact — `epic-001.plan.md` landed, the wrapper's post-bridge `id_propagate` and `epic_inject` ran. Confirms the timeout was inactivity-based, not wall-clock.

**Lesson**: any subprocess that runs longer than ~3-5 minutes silently is at risk of being killed by host-environment trackers (CI runners, IDEs, agentic UIs). Periodic stdout chatter is cheap insurance.

## Bug #3 — visibility gap (PR #7)

**Discovery**: during the 8-min and 27-min bridge runs, Kiro chat showed no activity at all — the long Bash invocation produces no visible output to the user. User asked "status?" three times in 10 minutes because they thought the task had finished and they needed to prompt again.

**Root cause**: `BRIDGE_PROGRESS` heartbeats (PR #6) keep Kiro's bash *tracker* alive but go to a buffer the user can't see. Kiro's chat UI does not stream the subprocess's stdout until it completes.

**Fix**: each long-running hook prompt (`on-requirements-saved`, `on-design-saved`, `on-tasks-saved`) now starts with an explicit **Step 0** instructing the agent to surface a visible chat line BEFORE running any Bash:

```
⏳ DLC: starting <verb> in the background — typically 5–10 minutes.
Don't re-prompt; I will surface results when the bridge completes.
```

`on-requirements-saved` gets a second mid-flight notice before Step 3 (review dispatch) for the same reason.

**Lesson**: when a host UI doesn't stream subprocess output, *narrate the future*: instruct the agent to print a clear status message *before* the silent gap, so the user has expectations set instead of guessing.

## Bug #4 — self-fire loop (PR #9, closes Issue #8)

**Discovery**: after the first `on-tasks-saved` fire successfully produced `epic-001.plan.md`, Kiro fired the hook *again* 2m30s later. The bridge cache *missed* (different source-content hash), spawning a redundant 8-min `plan-implementation`. Third self-fire happened a few minutes after that. ~\$6-9 of wasted API spend before manual intervention.

**Root cause**: the init wrapper's `id_propagate.propagate_ids()` and `epic_inject.inject_epic_dir()` BOTH mutate the trigger file (`tasks.md`). Kiro detects the mtime change as a `fileEdited` event and refires the same hook. The 30-second debounce window (NFR-14) had long since expired. The bridge cache is keyed on source-content hash — so any DLC-own write changes the hash and *misses* the cache.

This pattern affects all three save-hooks in principle: `id_propagate` writes back to `requirements.md`, `design.md`, and `tasks.md`. PR #5 made `id_propagate` actually work; that combined with `epic_inject` makes the self-fire surface every time.

**Fix**: a per-slug content-hash registry at `.dlc/<slug>/_self-writes.json`. After each successful init pipeline (post `id_propagate` + post `epic_inject`), the wrapper records `sha256(trigger_file)` — captures the post-init state regardless of which writer actually mutated the file. At init-stage entry (after debounce, before `invoke_bridge`), the wrapper compares the current trigger-file hash against the registry; on match within a 10-min TTL → emit `PROBE_SELF_FIRE` + `HOOK_INIT_SKIPPED`, return 0 without touching the bridge or any downstream step.

Up to 10 entries per file, TTL-evicted, adjacent-dedupe, `filelock`-protected, fail-open on lock timeout (same robustness pattern as `dlc_bridge.util.debounce`).

Bonus prompt cleanup: removed the now-redundant "Step 2 agent-side Epic markers" from `.kiro/hooks/on-tasks-saved.kiro.hook`. The Python wrapper's `epic_inject` step already handles this idempotently; the agent's manual edit was duplicating work AND was a primary self-fire trigger.

**Lesson**: in event-driven systems where your own actions can re-trigger you, *carry a memory of what you wrote*. Content hashes are cheap, last-N-with-TTL bounds the memory, and fail-open avoids deadlocking the system on registry corruption.

## Things that worked

- **Two-lane architecture (steering doc § Flow Orchestration)**: Lane 1 reviewers (security, a11y, ux) and Lane 2 bridge dispatch coordinated correctly through `state.md`. The PRD's "Recommended formal reviews" section (PR's "Section 13") correctly drove dispatch — performance was marked LOW and was correctly skipped, three relevant reviews ran in parallel.
- **Atomic state transitions**: every state.md update across the four hooks remained well-formed under multiple parallel fires and interruptions. No corruption.
- **Bridge cache**: when content hashes DID match (the third design-phase fire), the cache-hit short-circuit fired correctly in < 1s with the right `cache-hit` status file naming convention (`produce-tech-design-cache-hit-…`).
- **Background-mode infrastructure**: `cli.py` already supports `--background` + `background_runner.py` for long verbs. Not exercised in this run but available as a fallback if the inactivity-timeout pattern proves insufficient for a future verb.
- **Per-platform cross-CI matrix**: PR #5, #6, #7, #9 all passed on Linux + macOS for both Py 3.11 and Py 3.12 within a couple of minutes; the Windows runners were slower (sometimes still pending when admin-merged) but no platform-specific bugs surfaced in the code under test.

## Reproducer

To reproduce the e2e (or any portion of it):

1. Clone `kiro-bridge-poc` at `main` (post-PR-#9).
2. `uv sync --extra feedback` + `uv pip install aiosqlite` (the latter is missing from the `feedback` extras — see Bug-fix candidates above).
3. Open Kiro IDE in the repo, **`+` Specs** → create a new Spec with a brief like: *"Tiny FastAPI feedback collector — name, email, rating (1-5), free-text feedback. POST persists to SQLite. WCAG 2.1 AA, mobile-friendly, RFC 5322 email validation."*
4. Let Kiro auto-draft `requirements.md`; review and save inside Kiro. Watch `.dlc/feedback-collector/` for `requirements.prd.md` + analysis_output/ reports.
5. Advance to `design.md`. Watch `designs/tech-design.md`.
6. Advance to `tasks.md`. Watch `plans/epic-001.plan.md`.
7. "Run All Tasks". Watch `feedback_collector/` and `tests/` for produced code.
8. `uv run uvicorn feedback_collector.main:app --port 8765` to confirm the app runs.

Expected wall-clock budget: ~60–90 min if all four PRs from this session are in place; significantly more without (due to API spend on self-fire loops and orchestration confusion).
